# SkelCast

Use the project's `skelcast.config.mjs`, hints, and existing loading state. Read the package README for exact supported syntax and the project's boundary conventions before changing integration.

SkelCast's documentation, generated messages, developer tools, and examples use English. Preserve the application's original language when integrating existing source; recognizing localized loading labels does not authorize translating application content.

## Generation

- For an existing Vite React/Vue 3 app with SkelCast installed, use `pnpm exec skelcast init --dry-run --json` to inspect discovered pages, loading regions, and exact edits. Apply `pnpm exec skelcast init` within the user's requested integration scope. Init generates artifacts without executing application, router, Vite, or existing SkelCast config modules. Review route conventions and skipped patterns rather than treating discovery as proof of every loading relationship.
- Init preserves loading guards and early returns, writes backups and diagnostics under `.skelcast/`, and avoids duplicate boundaries on repeat runs. Dynamic configurations, other bundlers and SSR frameworks need explicit adapters; do not force a generic codemod through their diagnostics.
- Trace the target's render structure, CSS, imported components, and API field consumption. Identify text/image leaves, repetition, optional regions, and fields controlling classes, sizes, or branches.
- Business source is parsed only. Do not start the business application, authenticate, call APIs, import the business entry, or execute business functions to generate skeletons. The development config itself is trusted executable configuration.
- Init may add per-composable pending state only when source proves a single returned async API operation and its exposed reactive collection. It uses concurrency-safe `try/finally`; ambiguous ownership remains a diagnostic. Pages with `pending=false` are preview-only, not evidence of real loading integration.
- Reusable Vue request targets can carry finite `contexts` generated from caller source. Keep `data-sk-context`, the target mapping and the inner boundary `context` prop together. Audit actual request boundaries independently of page previews; one page-level match does not prove a nested request artifact. Dynamic/repeated callers need explicit finite contexts rather than guessed props.
- Choose explicit page/request boundary IDs. Use existing pending/route state; do not introduce a global network interceptor.
- Keep layout in business source. Add small hints for repeat count, text lines, fallback height, or bindings. For finite layouts, declare variants and their bindings before generation. Field names alone are not evidence of layout.
- For opaque local regions, use a source adapter if its layout is known; otherwise keep a visible local fallback and its diagnostic. Avoid inventing a detailed layout for arbitrary server-driven content.
- Vue auto-imports can be resolved from `GlobalComponents` declarations or explicit `components` mappings. Enable `styles.less`, `styles.unocss`, or `componentPresets: ['naive-ui']` only when appropriate for the application's source. UnoCSS accepts Mini/Attributify theme, shortcuts and safelist data; it does not execute the application's configuration. Preserve layout attributes, and review approximated third-party geometry and CSS `v-bind` diagnostics.
- Run `pnpm exec skelcast sync`, then `pnpm exec skelcast diagnose --id <id> --json`. Review diagnostics and evidence, repair relevant unknown layout decisions, and run `pnpm exec skelcast check`. Use `inspect --id <id> --json` only when raw generated HTML/CSS and metadata are needed. Generated modules and manifest are reproducible artifacts, not manual editing targets.
- Run `pnpm exec skelcast quality --json` to find empty variants, fallback regions and unresolved component tags independently of freshness checks. `--strict` fails for targets needing review. Structural counts do not establish painted geometry or similarity; verify representative layouts in a browser at desktop and mobile widths.
- CSS `v-bind()` resolves per instance from static props, defaults and bounded expressions. Use project-relative `componentBindings` for explicit theme/hook results; never invoke application hooks to obtain them. Variant bindings can target one component using `source/file.vue::expression`. Refresh explicit bindings after source theme edits and retain diagnostics for expressions that remain unknown.
- Declared Vue props, named slots, `v-model`, destructured loops and bounded collection callbacks can resolve source branches. Do not replace genuinely unknown outputs with empty values just to reduce diagnostics. Explicit storage/hook bindings describe a documented finite state, not the user's current persisted data.
- Keep real editors visible outside loading boundaries. Identify custom live regions with `data-sk-live` or `componentPolicies: { BindingName: 'live' }`. Never generate editor internals or an editor placeholder. `data-sk-preserve` retains static presentation only and cannot keep a real widget visible inside a hidden boundary. Resolve `LIVE_CONTENT_IN_BOUNDARY` by narrowing the source boundary. Known string `v-html` remains inert HTML. Preserve compact UnoCSS attributes such as `important:p0` and `px8`.
- Component library presets are opt-in and require a package/export identity from imports or component declarations. Never infer library membership from a tag prefix. Prefer resolvable local source and project adapters; keep finite library rendering and slot rules in their own modules. Do not add another library merely because its components exist in a project.
- Available basic presets are `naive-ui`, `element-plus`, `ant-design-vue`, `antd` and `vuedraggable`. Enable only the project's libraries. Mask loading data, not every visual component: keep buttons, labels, editable controls and calendar date-grid frames; replace data cells, images, statistics and read-only output. Use `data-sk-preserve` / `data-sk-mask` for local source overrides, and prefer request boundaries around data when live controls must stay interactive. Preserve hints do not execute or reconstruct unknown values.
- Default tables are bounded outlines: four rows, up to six columns, flat simple headers; `hints.repeat` overrides capacity. Skip cell callbacks, nested widgets, row values and exact text wrapping. Forms use basic control outlines without option-list expansion. Graphic components can use `componentPolicies: { BindingName: 'graphic' }`. Literal titles/instructions stay readable; dynamic text uses generic bars without original glyph strings. Do not repair intentional simplification as missing fidelity. Zero placeholders are valid when fixed content is readable.

## Repair a preview mismatch

- Use the developer's target ID, variant, viewport and description to scope work. Read `skelcast quality --json` for structural triage, then `skelcast diagnose --id <id> --json` for source locations, expressions, evidence and per-node repair examples across variants. These are source-only commands; they do not launch or authenticate into the application.
- Diagnose reports freshness. Sync stale/missing/modified artifacts before relying on source locations or examples; do not edit generated modules. Narrow a report with `--variant <name>` and `--node <source-node>` using IDs from the report. `--strict` makes unresolved review work fail for CI. Variant quality is whole-variant even when node context is narrowed.
- Trace the reported source and styles before changing values. Repair structural layout in source. For unresolved finite values, review and replace illustrative bindings with intended presentation values; examples do not establish business data. For opaque components, create a finite source adapter and merge its mapping into the existing target, retaining other mappings and settings.
- Save small shared hints with `skelcast hints --id <id> --file <patch.json> --json`, or edit the configured hints file directly. The patch is a JSON object for one target, with `repeat`, `lines`, `minHeight`, or `bindings`; paths are relative to `--root`. The command validates and saves without regeneration. Omitted fields and other targets remain intact. Supplied `bindings` replace the whole shared object: merge existing keys when retaining them, or use `{ "bindings": {} }` to clear. Explicit variant/component bindings still take precedence; edit variant configuration when the report identifies an override.
- Keep portable inspection artifacts self-contained. Production Vite builds externalize and deduplicate embedded images/fonts; check initial HTML and lazy artifacts under relative-base deployment when changing resource handling.
- Event-only directives and finite initial style writes are analyzed without running hooks. Unknown visibility-changing directives need declared `v-name.visible` presentation variants; never infer the user's real permissions. Test ready, empty and error variants against the corresponding real fixture state. Charts use region outlines; editors remain live outside the skeleton boundary.
- After corrections run `skelcast sync`, `skelcast check`, and the scoped `diagnose`/`quality` again. Preserve remaining unknowns honestly rather than silencing diagnostics with empty values or invented layouts. If intended geometry or business state is unknown, report what input is missing instead of repeatedly guessing.
- For geometry issues, use `skelcast audit --url <existing-dev-url> --id <id> --viewports 1440x900,390x844 --out <report-directory> --json`, or `auditBoundaryLayout` from `skelcast/browser` in the project's browser tests. Audit checks all generated variants, writes JSON/HTML and real/skeleton screenshots, and fails for drift or measurement errors. Read screenshot overlays as well as geometry; structural quality is not visual similarity. Use an existing Playwright `--storage-state` file if available for authentication. Browser audits run the application and can make real requests; they are separate from source-only generation. Keep reports and session files in project-appropriate local/test paths.
- Return the affected target/variants, concrete changes, validation results and any remaining limits. The developer uses the preview toolbar to compare and accept the result.

## Integration and preview

- React/Vue boundaries consume `virtual:skelcast/<id>` and real pending state. Guard missing business data. Preserve mounted state when toggling visual preview.
- Page targets inject initial HTML via the Vite plugin. Let a page boundary take over or call `releasePageSkeleton()` at an explicit ready point.
- Developers may run the business app, log in, and navigate to preview. `?__sk=page` holds page skeletons; `?__sk=<id>` holds one region; `__sk_variant` selects a generated variant. DevTools controls viewport sizes.
- The toolbar is for developer preview and visual acceptance: region picking, skeleton toggling, variants, content comparison, and brief generation status. It has no repair/diagnostic editor. Use project files and the CLI for corrections; do not ask the developer to edit JSON or repair examples in the toolbar. Do not ask the runtime/browser to infer a new skeleton.
- Verify normal loading and forced preview independently. Exiting preview must still show a skeleton when real pending remains true. Check responsive rules and fallback sizes, and ensure production output excludes development tooling.
- Verify that initial shells retire after mounting and SPA navigation, that theme variants follow the application's real theme state, and that horizontal content scrolls inside its own container. Check both real content and forced skeletons; page-wide overflow can be hidden by the application's outer layout.

Use light DOM when the component relies on business ancestor selectors. Shadow DOM is an optional style encapsulation backend; it does not remove the need to trace style context or prevent business execution.
